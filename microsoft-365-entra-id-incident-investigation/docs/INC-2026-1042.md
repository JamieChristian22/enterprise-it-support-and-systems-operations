## 4. Commands and outcomes

```powershell
Get-Module Microsoft.Graph -ListAvailable
Install-Module Microsoft.Graph -Scope CurrentUser -Repository PSGallery
Connect-MgGraph -Scopes 'User.Read'
Get-MgContext | Select-Object Account, TenantId, Scopes
Get-MgUser -UserId (Get-MgContext).Account | Select-Object DisplayName, UserPrincipalName, Id
Invoke-MgGraphRequest -Method GET -Uri 'https://graph.microsoft.com/v1.0/me'
```

The context-dependent `Get-MgUser` command failed because the `UserId` value was empty. The Graph `/me` request succeeded. Installation is a local workstation change; **no Entra tenant configuration was changed**.

## 5. Root cause and resolution

**Root cause of simulated M365 incident:** undetermined. No real Outlook/Teams/SharePoint error or successful retest was observed. **Root cause of Graph context anomaly:** undetermined. **Workaround validated:** direct authenticated Graph REST request returned the signed-in user's profile. This does not resolve the simulated workload access incident.

## 6. Recommended escalation

- Request exact app, timestamp, error code, correlation ID and device/network context from affected user.
- Check workload-specific interactive and non-interactive sign-in events, MFA and Conditional Access decisions.
- Confirm assigned product and service plans against intended entitlement and available license inventory.
- If license is required, seek authorized change approval; assign in Microsoft 365 admin center using an appropriately scoped account; then validate provisioning and end-user access.
- Investigate Graph context behavior with `Get-MgContext | Format-List *`, new PowerShell session and module-specific versions; avoid sharing tokens or personal identifiers.
- Review Global Administrator assignment against least-privilege policy; do not remove the sole recovery administrator without a recovery plan.
